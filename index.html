Federated Learning under Wireless Packet Loss

My MSc dissertation. Machine learning across many devices normally assumes that whatever a device sends, the server receives. Real devices upload over slow Wi-Fi, lose packets and miss deadlines. I built a simulator instrumented per device per round, modelling three separate network failure modes across compression schemes, four client-selection policies and two data distributions.

The result was that compression does not only reduce bandwidth cost. It changes which devices can take part at all. The accuracy gap between four selection strategies collapsed from 16.4 points to 2.3 once updates were small enough to arrive within the deadline.

Hard part
Telling a communication failure apart from a learning failure. If you only log accuracy, a configuration can look better simply because it excluded the devices hardest to hear from.
What I did
Instrumented every device every round and made each random draw a pure function of its inputs, so two configurations differing only in algorithm saw identical network conditions and their difference contained no channel noise.
What it cost me
Two defects surfaced in my own audit: a channel model where two arms differed in more than the variable under test, and an estimator receiving data it should never have seen. Both weakened my results. Both are in the repository changelog rather than quietly corrected.

Cloud-Native Bookstore Platform

A team project, six of us. The platform was a React front end against Catalog, Cart and Gateway services on Azure Kubernetes Service. My part was the client side: I built the catalogue, book detail, cart and checkout pages, and the browser-side authentication through Keycloak — parsing JWT claims into application state, refreshing tokens silently before they expired, and gating routes and admin actions on the user's role.

The wider platform, built by the team, covered blue-green releases, autoscaling and Velero-backed recovery. I co-authored the technical report documenting the architecture.

Hard part
Every cart action waited on a round trip, so adding an item felt sluggish even though nothing was wrong.
What I did
Applied quantity and removal changes to local state before the API responded, re-fetching on failure to recover consistency. That accepts a brief risk of the screen disagreeing with the server in exchange for an interface that feels immediate — on a cart, the right side of the trade.

AI Bias Audit Framework

A framework that measures gender, cultural and role-stereotype bias in generative-AI output rather than asserting it. Responses from several models are compared using TF-IDF, LDA topic modelling and Shannon-entropy diversity scores, so the claim "this model is narrower" comes with a number attached.

Hard part
Bias claims about LLMs are usually anecdotal, which makes them impossible to compare across models or to re-run later.
What I did
Fixed the prompt set and the metrics first, so a second run is a measurement rather than a new opinion.

Tokeneer Security Risk Assessment

A structured risk assessment of the Tokeneer secure-enclave system, mapping business risk to concrete technical threats — biometric spoofing, privilege escalation, enrolment-station compromise — and then to prioritised mitigations with the residual risk stated rather than assumed away.

Hard part
A threat list is easy; a defensible ordering of what to fix first, with a budget in mind, is not.
What I did
Scored each threat against NIST impact and likelihood criteria so the ranking could be argued with, not just presented.
